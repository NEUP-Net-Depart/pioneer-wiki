## 4. 优先完成数据正确性和权限闭环

### 完整发布快照与修订

- 把正文、双语标题与摘要、分类和其他元数据、封面、来源、标签、贡献者及关系纳入可恢复的修订合同。区分稳定的文章身份与可修订内容。
- 草稿和待审核版本不影响匿名读者或其他普通账号看到的发布版本，包括首页、文章、搜索、图谱、分类、成员文章列表和版本展示。
- 公开页默认始终展示公开版本；作者和管理员的未发布预览应在编辑／审核入口清晰呈现，避免因登录身份而把公开页混成编辑预览。
- 发布和回滚在数据库事务内完整更新发布快照、关联、指针和审计；回滚创建新修订，不改写已有历史。
- 双语提交校验应在业务层和数据库入口成立；公开历史仅暴露允许公开的修订，不能泄漏草稿或待审正文／元数据。
- 处理新条目 ID 和 slug 的冲突、并发分配、修改标题时 URL 稳定性，以及旧 URL 兼容。
- 管理员批准的是实际审阅的修订。审核期间作者再次修改、双管理员发布、归档和发布同时发生，都不能默默发布未审内容或覆盖更新。
- 老迁移不直接改写；通过新迁移兼容已有数据。明确历史快照缺失时可以恢复哪些字段，不要伪造旧版本元数据。

### 身份、生命周期与审计

- 服务器和数据库共同执行匿名、未验证读者、已验证读者、绑定作者、管理员、停用账号的权限矩阵。数据库直接调用不得绕开 HTTP 检查。
- 客户端不能指定操作人、授权角色或冒用作者／成员；继续由数据库会话派生论坛身份，保留线程与首帖原子性。
- 建立可靠的一致身份关系，解决 `profiles.member_id` 与实际按 `author_id` 查找成员的双重口径；用约束和事务防止不存在目标、重复绑定、错绑和部分成功。
- 管理员必须具备可用的文章管理能力，首次管理员引导完成后能实际建稿、审核和发布。不要要求运营者手写 SQL 才能完成初始化后的日常操作。
- 停用／撤销权限后，旧会话和直接数据库请求不能继续写入。最后一位有效管理员不能被并发操作移除、停用或注销。
- 重要管理操作与审计原子化；不能更新成功、审计失败却仍返回成功。审计记录主体、动作、对象、时间和必要差异，避免记录凭据和无关个人信息。
- 普通内容操作使用授权 RPC/RLS。只有确实需要 Auth Admin API 等服务权限的操作才使用服务端 service-role；入口仍须鉴权，密钥不得进入客户端或日志，不得以 service-role 绕过正常内容授权。

## 5. 完成可通过网页运营的业务模块

### 账号和成员资格

- 打磨注册、登录、邮箱验证、重发、找回密码、重设密码、退出和账号设置。处理邮件过期、重复点击、重复账号、网络失败、会话过期和可恢复的认证错误。
- 账号设置可修改公开展示资料，并通过供应商确认机制更换邮箱、修改密码；账号 handle、作者 handle、成员 handle 的关系必须清楚，保护现有公开 URL。
- 读者能够从账号页提交作者／成员资格申请、查看处理状态；管理员能够审核、说明拒绝原因、创建或选取作者／成员并绑定。重复申请和重复点击必须安全。
- 管理员具有带分页、搜索和状态筛选的账号管理，能够查看绑定关系、停用／恢复、解绑以及授予／撤销管理员。
- 注销申请具有可见状态和管理队列；完成匿名化、公开身份处理和登录撤销。保留历史文章修订与必要审计，处理署名、论坛归属、上传资源和外键，不因删除 Auth 用户造成数据损坏。
- 对 Auth 与数据库之间无法单事务完成的操作提供可重试的状态和幂等处理，不用一个虚假的 `ok` 掩盖半完成结果。

### 文章与审核工作台

- 提供全量文章管理与作者的“我的文章／草稿”，支持搜索、分页和状态筛选，以及创建、编辑、预览、查看历史、提交、退回修改、发布、回滚、归档和恢复。
- 审核同时展示正文和元数据差异、提交人与时间、公开版本和待审版本；退回原因能让作者看到并继续修改。
- 发布、退回、回滚、归档均有清楚的作用范围和结果反馈；需要确认的操作使用站内对话框。审核后保持合理的列表位置和筛选状态。
- 保留并完善本地恢复缓存、服务端工作草稿和同步状态；正确处理 metadata-only 修改、断网、401、存储容量限制、跨设备和多标签冲突。旧自动保存请求不能覆盖较新结果。
- 登出、换账号时不能恢复另一个账号的私人草稿。保存失败保留输入；重新登录后应能安全继续。
- 新来源和新标签的编辑、审核与落库须真正闭环；不能在界面中允许填写却只把字符串留在草稿里。

### 友链

- 提供专用管理界面及领域校验，维护双语名称和介绍、HTTP(S) 地址、徽记和加入日期等现有字段；不让运营者直接编辑原始数据库 JSON。
- 新增、修改、归档、恢复立即反映在公开目录和地图；处理重复地址、非法协议、长名称、空列表和友链数量增长。
- 保持可预测的顺序，核查地图的领地分配；增删内容后不应出现索引／地图错位或链接错误。

### 成员个人页面

- 管理员能创建、编辑、绑定、归档和恢复公开成员；本人能从账号菜单／账号页到达自己的主页与编辑器。
- 管理员和本人复用已有编辑组件及校验合同，并通过明确能力区分操作，保留封面、藏书票、简介、Markdown、链接、GitHub 和作品管理。
- 明确归档主页的公开响应、本人提示、编辑限制和关联内容的署名展示。恢复不丢失作品、藏书票或绑定信息。
- 主页变更历史能用于恢复内容；不要仅在审计里堆完整 JSON 却不给运营者理解变化的方式。

### 图片、素材及现有公共板块

- 提供文章图片的批准／拒绝、版权与替代文本信息管理，保护审核状态；文章发布前检查所引用图片是否可公开使用。
- 区分“素材记录审核”和“对象是否公开可访问”。若图片处于待审状态，公开 Storage URL 不能被误当成私密保护；实现与审核规则一致的访问策略。
- 上传验证类型、文件大小和像素限制，使用现有 WebP 重编码；处理上传成功但写记录失败、替换失败、重复请求、旧文件仍被引用和孤立资源清理。归档不立即删除资源，不清理仍被历史修订引用的素材。
- 公共论坛上线必须有基本治理：管理员可隐藏／恢复违规主题或回复、锁定／解锁主题，停用账号不能发帖。身份、首帖事务和并发编号规则继续成立。
- 纪行作为现有公开板块，补齐管理员新增、编辑、归档和恢复入口，沿用现有双语内容、参与者、资源与图片合同；不新增活动报名或通知系统。
- Mock 与 Supabase 都须遵守同一服务合同。测试用 Mock 保持确定性；依赖真实认证或 Admin API 的能力没有配置时明确提示不可用，不能假成功。

## 6. UI/UX 打磨是同等交付目标

延续项目的博物志与编辑室气质：纸张底色、墨色文字、衬线标题、细分隔线、编号、藏书票、安静的色彩和克制动效。以现有 tokens、paper、sheet、NotebookSheet、DraftingSheet 和 shadcn/Radix 基础组件为依据。后台可以更紧凑高效，但应与公开站点属于同一套设计。

请完成实际的信息架构和交互设计，不要套普通 SaaS 的统计卡片后台。管理主入口应让人清楚找到审核、文章、账号／资格申请、成员、友链、分类、素材、论坛、纪行、回收站和审计；按任务分组，用必要的计数帮助处理待办，不用无意义图表填充首页。

- 账号菜单和每个工作台有正确的权限可见性、当前所在位置、返回入口和完整页面标题。无权限、未绑定和未验证用户有清楚的下一步。
- 表单分组、标签、帮助文字、必填提示、行内错误和提交结果一致；焦点引导到首个错误，保留用户输入和修改状态，支持离开提醒。
- 异步操作具有 loading、disabled、防重复提交、成功、失败和重试反馈；列表不能把接口故障显示成“没有数据”。避免保存后整页 reload 造成失焦、丢滚动位置和闪烁。
- 权限错误不堆数据库异常，双语文案解释当前状态和下一步；错误响应保留可诊断的安全错误码。
- 区分“保存草稿”“提交审核”“发布”“归档”“停用账号”，按钮和确认文案准确表达后果，不复用模糊的“确定”。归档和敏感角色变更说明对象及影响。
- 对恢复、待审核、退回、同步失败、账号停用、身份未绑定、空回收站等状态做完整设计。
- 桌面表格在手机上有可读的布局；320px、390px、768px、1440px 均可完成核心任务。注意长英文、长 URL、长标题、双语标签和触控目标。
- 键盘可操作所有控件，保留可见 focus；对话框焦点约束和关闭后焦点恢复正确；消息可被辅助技术感知，颜色不能是唯一状态线索。
- 保持 WCAG AA 的关键对比度、正常字号和舒适行距，支持 200% 缩放及 reduced-motion。不为了装饰新增大体积图片或动画。
- 检查公开页、认证页、编辑器和后台的过渡、滚动、层级及固定导航遮挡，实际操作中修复问题；不要只检查首次加载截图。

## 7. 生产运行和部署交付

- 生产必须显式使用 Supabase，配置缺失或数据库不可用时清晰失败，不能静默转成会丢数据的 Mock。
- 核查生产域名和代理下的邮件 callback、允许的 redirect、Cookie、安全退出及 SSR 会话续期；使用受信任的站点基地址生成回调，避免任意 Host/next 导致跳转错误。
- 为注册／重发／找回、论坛写入和图片上传配置实际有效的频率及资源限制。说明 Supabase 自带限制与本站限制的分工；若存在直连数据库写入口，不能只在 HTTP 层限流。考虑代理地址和多进程部署，不把单进程 Map 宣称为可靠生产限制。
- 检查 cookie 写请求的跨站保护、输入边界、Markdown 和链接安全、成员作品预览的 SSRF 防护，维持现有防护和授权。
- 提供轻量 liveness/readiness 和适当的故障可观测性，不公开秘密、账号信息或完整错误栈。区分进程活着与数据库就绪，避免数据库短暂故障导致无意义重启风暴。

## 9. 交付方式与停止条件

按以下顺序推进：完整发布快照和权限 → 账号／身份管理 → 内容管理与归档恢复 → 素材和现有公共板块运营 → UI/UX 迭代 → 全链路与部署验证。发现相邻的真实阻塞问题时一并处理，在清单中说明原因。

任务较大也请持续执行，分阶段建立可检查的成果，不要在完成一张页面或几个 API 后结束。耗尽单次上下文前留下准确进度、当前分支、改动、测试和下一步，让续接能够继续，不从头重复。

最终交付：

- 完整实现的本地代码、新迁移、测试、必要的环境和部署文档；业务核心不能留 TODO、假成功、死按钮或运营必须手写 SQL 的缺口。
- 简洁的权限矩阵和状态流转说明，说明旧数据兼容、历史快照限制、迁移顺序和恢复方式。
- 按验收清单报告完成、失败和未执行，附实际命令结果与浏览器证据；明确哪些是真实 Supabase 测试，哪些只是 Mock。
- UI 截图与关键用户操作说明，涵盖账号、管理员工作台、文章审核、友链、成员管理和回收站，含手机布局。
- 生产上线前仍需维护者执行的准确步骤、所需配置和授权；区分可部署交付与实际生产上线。

只有当网页操作、数据库授权、持久化、归档恢复、审计、UI 状态和验证证据都闭环时，才能称为实现完成。有任何未修复的生产阻塞或未执行的必要验证，明确列出，不能用“基本完成”“后续优化”掩盖。

请现在开始执行。先核对仓库状态和关键源码，简要给出证据支持的实施顺序，然后立即继续实现。
